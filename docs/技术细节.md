## 一、核心工程问题与解决

这一节是项目的技术价值所在。每个问题都是**实际踩出来的**，不是设计时想到的。

### 1.1 音频链路：G.711 μ-law 没有唯一标准表

实现 μ-law 编解码时遇到一个反直觉的坑：网上大量资料说"字节 0x00 表示最大正电平"，
但实测相反，导致一度以为实现有 bug。

**排查方法**：用 Python 标准库 `audioop`（独立权威实现）逐条对照：

| 线性值 | 本实现 / `audioop` |
|---|---|
| +32124 | 0x80 |
| −32124 | 0x00 |
| 0 | **0xFF**（静音） |

**结论**：G.711 μ-law 存在**多种历史变体表**，网上流传的"0x00=最大正电平"属于 AD&D 变体。
**必须用权威实现校准，不能靠查表。**

> 附带收益：用"过零次数"验证重采样后的音高正确性（440Hz 一秒应约 880 次过零），
> 比"能出声就算对"可靠得多。

### 1.2 二进制处理的隐蔽陷阱：`Buffer.from(Float32Array)` 不遵守 byteOffset

送进识别引擎的音频必须转成 base64 的 float32。最初的写法是：

```js
Buffer.from(float32Array).toString('base64')
```

单元测试发现：**本该 1280 字节的音频变成了 3427 字节，解出来的浮点值是 1e31 量级的垃圾。**

**根因**：`Buffer.from(typedArray)` 是"共享同一块内存的视图"，
而 TypedArray 若来自内存池会带非零 `byteOffset`，
于是 `Buffer.from()` 把池中 `byteOffset` 之前的无关内存一起编了进去。

**正确写法**：

```js
const bytes = new Uint8Array(f32.buffer, f32.byteOffset, f32.byteLength);
Buffer.from(bytes).toString('base64');
```

**这个 bug 的可怕之处**：它不会报错、不会崩溃，数据"看起来有内容"，
只是**全是垃圾**——如果不是逐个校验浮点值范围，它会一直潜伏到接上硬件才发现。

### 1.3 读取压缩会话文件：为什么"文件是空的"

需要检测"AI 这一轮回复完成"，方案是只读监听它的会话文件。
第一次尝试时，用 Node 解压得到 **0 字节、2 行**，看起来文件是空的。

**根因**：该会话文件是 **多个 zstd frame 拼接**的，
而 Node 的 `zstdDecompressSync` **只解第一个 frame**。

**解决**：按 zstd 魔数 `28 B5 2F FD` 切分 frame，逐个解压后拼接。
实测 **6166 个 frame 全部成功**，解析出 15 个回合、14 个已完成。

> 另一个发现：Node 的 zstd 对**截断的 frame 是容错的**——不抛错，只返回已解出的部分。
> 所以"正在写入的半截 JSON 行"会被 JSON 解析自然跳过，等写完下次轮询自动补上，
> 不需要任何特殊处理。

### 1.4 如何可靠地识别"这一轮说完了"

会话文件里有两类关键事件：

| 事件 | 含义 |
|---|---|
| `turn/end` 且 `reason.kind == "completed"` | **这一轮结束的可靠标志** |
| `assistant/message` | 助手的产出；一个回合可能有**多条**（分步产出），按序号取**最后一条**才是最终答复 |

**关键设计**：不能见到回合完成就响铃——用户自己打字时也会产生回合，
那样每次敲键盘都会被电话打扰。

**解决**：进入等待状态时记录一个**时间下界**，只对下界之后完成的回合响铃。
实测验证：历史 14 个回合全部被正确排除。

### 1.5 Windows GUI 自动化的两个坑

向输入框注入文字需要：找到窗口 → 聚焦 → 粘贴 → 回车。踩到两个坑：

**坑一：PowerShell 脚本必须全 ASCII。**
Windows PowerShell 5.1 会把**无 BOM 的 UTF-8 文件按 GBK 读取**，
脚本里的中文全部乱码，直接导致语法错误。

**坑二：块注释里不能出现 `#>` 序列。**
它在块注释内部会**提前结束注释**，后面的内容全部被当成代码解析。
（这个坑让我多花了一轮才定位到。）

### 1.6 GPU 环境：`is_available()` 返回 True 不代表能算

在新架构显卡上（sm_120），PyTorch 的 `torch.cuda.is_available()` 仍会返回 `True`，
但如果编译时没有包含对应架构的内核，
**第一次真正执行计算**才会抛出 `no kernel image is available`。

**解决**：写冒烟测试，实测 8 类核函数（matmul fp32/bf16/fp16、conv1d、LayerNorm、softmax、einsum）是否真的能跑，
并检查 `torch.cuda.get_arch_list()` 是否包含本机架构。

### 1.7 一个被放弃的功能：本地语音合成

原计划让 AI 的回复**从听筒里念出来**。实测后放弃。

**实测数据**：本地 TTS 模型（Qwen3-TTS 0.6B）只有 **0.31x 实时率**
——生成 1 秒音频要 3 秒。尝试过的优化与结论：

| 尝试 | 结果 |
|---|---|
| 换注意力实现（manual / sdpa / eager） | 差异仅 ±20%，**不是瓶颈** |
| 换采样参数 | 无效 |
| 定位瓶颈 | 该模型有 **16 个码本，每帧需串行预测 15 次** —— 每秒音频约 180 次前向，**架构上注定慢于实时** |

**根本原因**（调研结论）：
- 该类模型在 Transformers 路径下的 RTF 本就是 2.64（0.38x），
  只有切到 **Linux + vLLM** 才能到 6 倍速——而 vLLM 不支持 Windows；
- 更普遍地，**Windows 的 WDDM 图形调度**让每次 kernel 启动延迟高一个数量级（20–50µs），
  而自回归解码每步有几十个串行小 kernel，开销被成倍放大。

**决策**：放弃听筒播报，回复内容看屏幕即可。
（已调研出替代方案：纯 CPU 的 ONNX 非自回归模型可达 70x 实时率，且部分模型**原生 8kHz 输出**，
正好匹配电话；将来需要时可低成本加回。）

## 二、验证方式

### 不依赖硬件的完整闭环验证

项目内置一个"模拟网关"：用软件模拟一台话机**摘机拨号、推送音频、挂机、接听回铃**，
把整条链路真跑一遍。

实测输出：

```
idle → ready（摘机，播就绪音）→ listening
     → transcribing → 识别结果: "……"（时延 137ms）
     → submitting → 已提交 → idle
     → ringing → ★ 发起回铃 → 模拟网关收到 INVITE ✓ → answered
统计: calls=1, submitted=1, rings=1, answered=1
```

**这是本项目最有价值的一环**：它让"接上硬件才发现问题"变成"接上硬件只是最后一步"。

### 测试规模

**146 项单元与集成测试**（`node --test "src/**/*.test.mjs"`），覆盖：

音频编解码与重采样、SDP 生成与解析、SIP 消息解析与畸形输入、
来电/挂机/取消完整流程、**未接听去电的 CANCEL 撤销**、DTMF 收号、
识别协议构造与超时、状态机的每一条边界（录音过短、**整段静音**、识别失败、
空文本、提交失败、超长录音、**按次数响铃**、回铃超时/被拒/总开关）、
会话解析（多 frame、截断帧、乱序消息、**多会话定位**、**锁定等待回合**）、
注入器的错误分类与重试、以及一堆**真机踩过之后补的回归测试**。

另外还有几个面向真机的验证脚本（在 `源码/phone-companion/工具/验证/` 下），
其中 `验证真机响铃.mjs` 会**直接让话机响**（用临时端口，不影响正在跑的服务）：

```bash
node 工具/验证/验证真机响铃.mjs 5        # 让话机响 5 秒
node 工具/验证/验证通知铃.mjs 1          # 验证"响 1 声后自动挂断"
node 工具/验证/验证回铃链路.mjs           # 真状态机 + 假话机，端到端 12 项断言
```
