### 🔴🔴 真机联调踩到的头号大坑（2026-09-17）

**SIP 的 2xx 应答必须带 `Contact` 头。**

对端靠 `Contact` 决定"后续请求（ACK/BYE）发到哪个地址"。缺了它：

- 设备**不会回 ACK** → 通话建立不起来
- 设备的实际表现：**持续重拨 + 播放快速忙音**（用户听到的就是这个"重复提示音"）
- 我们这边的表现极具误导性：日志显示"摘机 → 开始收音 → 进入 listening"一切正常，
  但 `audioRxFrames: 0`（一个音频包都收不到）

**定位方法（值得记住）**：拿一个"**已被证明能工作**的最小实现"，与出问题的实现
**逐字节对比报文**。这次就是靠 `工具/报文对比.mjs` 一眼看出差的正是 `Contact` 那一行。

- 对比脚本：`工具/诊断/报文对比.mjs`（离线对比两种构造）
- 现场验证：`工具/验证/验证在跑的服务.mjs`（对运行中的服务发模拟 INVITE，校验回包）
- 回归测试：`src/sip-endpoint.test.mjs` 里已加断言锁住该行为

### 🔴🔴🔴🔴 回铃链路的两个断点（2026-09-17，第四个真机 bug）

**现象**：输入链路全通（识别准、提交成功、用户收到消息），**但我回复完电话不响**，且**日志里连一行回铃相关的输出都没有**。

**根因是两个漏洞叠加**，单独修任何一个都还是不通：

| # | 漏洞 | 后果 |
|---|---|---|
| ① | `PhoneMachine._transcribeAndSubmit()` 保存了 `this.replies`，却**从不调用 `replies.arm()`** | 监听器一直待机，`completions` 恒为 0 |
| ② | `buildService()` 里**没有把 `watcher.on('reply-completed')` 接到状态机** | 即使检测到完成，也没人发起呼叫 |

**为什么难发现**：监听器没被激活是"静默"的——它照常轮询（日志显示轮询 11523 次），
只是永远不会判定完成。而且没有报错。判断依据是快照里的 `armed: false / completions: 0`。

**修复**：
- 状态机在提交成功后调用 `this.replies?.arm?.()`
- `buildService()` 里绑定 `reply-completed → machine.onReplyCompleted()`，
  并用 `service._ringBound` 做幂等保护（**重复绑定会导致一次回复响铃多次**）

**顺带修的健壮性问题**：Node 的 `emit('error')` 在无监听器时会**抛异常**，
在常驻服务里等于"一个错误事件就杀死进程"。已在 `PhoneMachine` 构造函数里挂兜底监听器。

**验证工具**：`工具/验证/验证回铃链路.mjs` —— 串起真 SessionWatcher + 真 PhoneMachine + 假 ATA，
人工制造"回合完成"事件，断言电话被呼叫（**12/12 通过**）。

### 🔴🔴🔴🔴🔴 回铃链路的第三个断点：启动时把"正在进行"的回合也标成已见（2026-09-17）

前两个断点修完之后**仍然不响**。第三个根因在 `SessionWatcher.start()`：

```js
// 错误写法：无差别地把所有回合都标记为已见
for (const t of snapshot.turns) this._seenTurns.add(t.turn);
```

`start()` 时那个**正在进行、尚未完成**的当前回合也被标记成"见过了"，
等它真正完成时被 `poll()` 直接跳过 → 永远检测不到完成。

**为什么离线测试测不出来**：测试造的会话文件里事件都是完整的，
不存在"启动时正处于半截"的状态。**只有真机必现。**

**修复**：只把 `t.completed === true` 的回合标记为已见，
并在 `ready` 事件里报告 `{turns, seen, completed}`，让这件事在日志里可见。

**回归测试**：`src/phone-replies-regression.test.mjs`
（启动时留一个未完成回合 → 之后补上 `turn/end` → 必须被检测到）。

**顺带补的诊断**：`buildService()` 里给 `watcher.on('ready')` 加了日志，
启动时会打印：

```
[监听] 会话已载入：30 个回合，已完成 28（记为已见），进行中 2（完成后会响铃）
```

以前这一行根本不存在，只能靠读源码猜——这正是第三个 bug 难定位的原因。

### 🔴🔴 全项目复查又挖出两个真 bug（2026-09-17 收尾扫尾）

#### ① 启动器"有时候起不来"的真凶是路径算错一层

`启动.mjs` 就在 `phone-companion\` 里，但它写的是 `const PROJECT = join(HERE, '..')`
—— 那是"假设本文件待在 `源码\` 下"的算法。目录重组后 PROJECT 变成 `源码\`，连锁全错：

| 后果 | 证据 |
|---|---|
| 拉起电话服务时 cwd=`源码\`，找不到入口 | `源码\.runtime\phone.err.log`：`Cannot find module '...\源码\src\phone-control.mjs'` |
| CAPSWRITER 指向不存在的 `红色座机语音终端\CapsWriter-Offline` | 识别服务也起不来 |
| `.runtime` 建在 `源码\` 下，而服务把心跳写在 `phone-companion\.runtime\` | 启动器读不到心跳 → **明明在跑却报"已退出"** |

**这个 bug 长期被误判成"detached spawn 在 DSH 托管的 shell 里起不来"**（见下文"启动器已知问题"，
那条结论是错的，已作废）。修法：`PROJECT = HERE`。

顺带把启动器改可靠了：
- 运行状态以**服务自己写的心跳**（`.runtime/phone-status.json`，每 5 秒刷新）为准，
  不再只看 `pids.json`（那只记得本启动器拉起的那个进程，服务被别的方式起过就是一条过期记录）
- `--stop` 会等端口真正释放（否则紧接着 `start` 会被误判成"已在运行"）
- 端口被占用但不是我们的服务时，明确报警而不是假装"已在运行"

#### ② "打过一次电话之后，电话就再也不响了" —— 幽灵通话永久占线

**根因**：通话只靠**对端发 BYE** 收尾。而对端异常消失（拔线、断电、丢包）时不会发 BYE，
`this.call` 就一直留着 → `isBusy` 恒为 true → 之后**所有回铃**都被 `line-busy` 挡掉，
状态机也永远卡在 `listening`。

**这次的触发者是我们自己的验证脚本**：`工具/验证/验证在跑的服务.mjs` 发完 INVITE
拿到 200 OK 就直接 `process.exit()` —— **没发 ACK、没发 BYE**，于是每次跑完验证，
用户的电话就废了。这个脚本之前"通过 9/9"，却留下了一个坏掉的服务。

**两处修复**：

1. **验证脚本自己收尾**：校验完补发 `ACK` + `BYE`。
2. **服务端加兜底** `SipEndpoint.sweepStaleCall()`，由服务的 5 秒定时器周期调用：
   - 通话建立后**一个音频包都没收到**、且超过 120 秒 → 判定僵死
   - 曾经收到过音频、之后完全静默超过 300 秒 → 对端中途消失
   - 判据刻意只看"完全没有任何 RTP"，不做静音检测，**用户中途不说话不会被误杀**
   - 清掉时照常抛 `call:ended`，状态机自动收尾回 idle

回归测试：`src/sip-endpoint-stale.test.mjs`（5 项，含"正常通话不能被误杀"的反向断言）。

#### ③ 回铃目标会被自检脚本"学"成本机自己（2026-09-17 验收当天发现）

回铃目标地址是从"刚才谁打进来"学习来的（这是对的——比写死的配置更可靠）。但
`工具/验证/验证在跑的服务.mjs` 是**从本机地址**往 5090 打模拟 INVITE 的，同样触发 `call:incoming`：

```
[回铃] 目标地址从配置的 172.50.1.103 更新为来电实际地址 172.50.1.2   ← 被污染成本机了
```

后果：回合完成时 INVITE 发给我们自己 → **电话不响，而且日志看起来一切正常**
（目标地址被悄悄改掉，没有任何报错）。所幸紧接着真机来电又把它改回了 `172.50.1.103`，
所以验收没被影响——但如果先跑自检、再来回合完成，电话就哑了。

**修复**：只从**非本机来源**的来电学习目标。来源地址等于本机地址或回环地址的一律忽略，并打日志说明。

#### ④ 回铃改成「通知铃」，并挖出"去电从不发 CANCEL"这个高危 bug（2026-09-17 用户验收后）

**用户需求变更**：回铃不再需要走过去接听 —— **响约 5 秒自动挂断**，铃声本身就是"我说完了"的信号。

两处一起改才成立：

| 改动 | 值 | 为什么 |
|---|---|---|
| `ringTimeoutSeconds` | `20 → 5` | 响 5 秒自动收线 |
| 网关铃音节奏 `P4010`–`P4019` | `c=2000/4000;` → `c=1000/1000;` | **原本是"响 2 秒停 4 秒"，5 秒窗口里只会响 2 秒** —— 只改超时的话根本听不到"响 5 秒" |

另加总开关 `ringbackEnabled`（`false` 时一声都不响），用户可随时自行暂停/恢复。
超时也会清掉 `pendingReply`（否则 status 永远显示"有（等我说完就会响铃）"，看着像卡住）。

##### 🔴 顺带挖出：没被接听的去电从来没有被取消过

**症状**：连续试铃几次之后，呼叫永远返回 `486 Busy Here`，而网关状态页显示端口是"**挂机**"
（所以不是话机没挂好）。用户随即要求"暂停响铃"。

**根因**：`SipEndpoint.hangup()` 只有一句 `if (!this.call) return false`。
而 `this.call` **只在对方接听（200 OK）时才被赋值**；没人接的去电只存在于 `_outgoing` 里，
于是挂断动作是**纯空操作，一个包都没发**。

后果是双向的：

- 对端（HT801）一直把话机振铃、线路一直显示忙 → 后续所有呼叫 486
- **用户要的"响 5 秒自动挂断"正好走这条路**（没人接也要收线）→
  不修的话通知铃会一直响到网关自己的 60 秒超时，并把线路长期占死

**修复**：`hangup()` 分两种情况处理 —— 已接听发 `BYE`，未接听发 **`CANCEL`**
（按 RFC 3261 必须与那条 INVITE 同 branch / 同 Call-ID / 同 CSeq 序号）；
并对撤销后收到的 `487 Request Terminated` 补 `ACK`（否则对端会一直重传），
且不把它误报成"呼叫失败"。超时未应答的撤销上下文由 `sweepStaleCall()` 清理。

回归测试：`src/sip-endpoint-cancel.test.mjs`（8 项）。

### 🔴🔴🔴 注入环节的坑（2026-09-17，第二个真机 bug）

**现象**：电话链路全通（识别成功、日志显示"已提交"），但**用户看不到文字**。

**根因**：注入脚本里的 `Focus()` 每次都会"Alt 轻敲"一下，用来绕过 Windows 的前台锁定规则。
但当目标窗口**本来就在前台**时，这一下 Alt 把**焦点推到了浏览器自己的界面上**
（Edge 落到菜单按钮 `BrowserAppMenuButton`），于是 `Ctrl+V` 粘到了浏览器 UI 而不是网页输入框。

**表现极具欺骗性**：脚本报告 `pasted 37 chars` + `sent ENTER`，看起来完全成功。

**定位方法**：用 **UI Automation 读焦点控件的类型**：

```
修复前: CLASS=BrowserAppMenuButton  TYPE=ControlType.Button   ← 焦点在浏览器界面
修复后: CLASS=uV2eYG_input          TYPE=ControlType.Edit     ← 焦点在网页输入框
```

**修复**（两处）：
1. `Focus()` 先判断是否已在前台，**是就什么都不做**（绝不敲 Alt）；
2. 粘贴前检查焦点控件，若落在浏览器 chrome 上，**先按 Esc 把焦点还给页面**。

诊断工具：`工具/诊断/注入诊断.mjs`（逐步验证：找窗口 → 前台 → 剪贴板 → 焦点 → 输入框内容）

## 四、关键技术结论（踩过的坑，别重犯）

1. **μ-law 没有唯一标准表** —— 网上流传的"0x00=最大正电平"是 AD&D 变体。
   本实现以 Python 标准库 `audioop` 为权威基准校准：`0x80`=最大正，`0xFF`=静音。
   校验脚本：`工具/研究与调试/μlaw标准校验.mjs`

2. **Node 的 `zstdDecompressSync` 只解第一个 frame** —— 而 DSH 的 `session.jsonl.zstd`
   是多 frame 拼接，直接调用会得到 0 字节、看起来像空文件。
   **解法**：按 zstd 魔数 `28 B5 2F FD` 切 frame 后逐个解压。
   实测 6166 帧全部成功。实现在 `src/phone-replies.mjs` 的 `decompressSession`。

3. **`Buffer.from(Float32Array)` 不遵守 byteOffset** —— 会把内存池里无关数据一起编进去。
   实测本该 1280 字节变 3427 字节、float 值成 1e31 量级 → 识别必然失效。
   **必须**走 `new Uint8Array(f32.buffer, f32.byteOffset, f32.byteLength)`。

4. **"回复完成"的可靠标志** = 会话里的 `turn/end` 事件且 `data.reason.kind === "completed"`。
   一个回合有多条 `assistant/message`（分步产出），**最后一条**（按 seq 最大）才是最终答复。

5. **只对"电话发起的回合"响铃** —— 用 `arm()` 记录时间下界，只响铃下界之后完成的回合，
   否则用户自己打字时会被电话打扰。

6. **本地 TTS 不可用于实时对话** —— Qwen3-TTS 0.6B 实测 **0.31x 实时率**。
   根因：16 个码本、每帧需串行预测 15 次，约 180 次前向/秒音频。
   已排除：换注意力实现（manual/sdpa/eager 差异仅 ±20%）。**换引擎才有救，非调参可解。**

7. **GPU 环境** — `torch 2.8.0+cu129` 编译含 `sm_120`，与本机 Blackwell 完全匹配；
   但 `is_available()` 返回 True 不代表能算，必须实测核函数（`tts/cuda冒烟测试.py`）。

8. **PowerShell 脚本必须全 ASCII** —— 5.1 会把无 BOM 的 UTF-8 文件按 GBK 读，
   中文全乱导致语法错误。另外**块注释里不能出现 `#>` 序列**（会提前结束注释，
   后面全被当代码解析）——这个坑让我多花了一轮才定位到。

9. **DSH 会话文件在 `<会话id>/` 子目录里**，不在工作区编码目录下：
   `<sessions>/<工作区编码>/<会话id>/session.jsonl.zstd`。
   工作区路径 → 目录名的编码规则：盘符冒号去掉、分隔符→`-`、空格→`~0020`、整体用 `--` 包裹。

10. **回铃目标地址应从来电里学** —— 配置里写死的网关地址在换网段后会失效，
    而"刚才谁打进来"永远是对的。已在 `buildService` 里做了自动更新。

11. **Node 的 zstd 对截断 frame 是容错的** —— 不抛错，只返回已解出的部分。
    所以正在写入的半截 JSON 行会被 `parseEvents` 自然跳过，等写完下次轮询补上，
    不需要特殊处理。
