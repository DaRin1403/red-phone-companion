## 0. 结论先行

**你说的模数转换器，只是三件事里的一件。** 一台"电话录音盒"确实就是标准的 A/D 设备（RJ11 → 隔离变压器 → USB Audio ADC，Windows 里直接显示为 USB 声卡）。
但它解决的是 **①声音进电脑**；你requirement ②（像真打电话）还需要 **②声音出到听筒** 和 **③摘机/挂机/振铃这些"电话语义"**。

这三层可以**分开买**，也可以**一个设备全包**。买哪种，决定了这个项目是"150 元的动手项目"还是"600 元的开箱项目"。

| 路线 | ①声音进电脑（A/D） | ②声音出到听筒（D/A） | ③电话语义（摘机/挂机/振铃） | 价位 | 成功率 | 像真电话 |
|---|---|---|---|---|---|---|
| **★R0 听筒直连 RJ9→USB 适配器**（调研后新发现，强烈推荐） | ✅ 标准 UAC 声卡，全双工 | ✅ 推得动听筒喇叭 | ❌ 摘机信号要另加（叉簧开关） | **100–330 元** | **95%** | ✅ 听感是原生电话听筒 |
| R1 纯 A/D 录音盒 | ⚠️ **故意不暴露成声卡**（私有协议+签名驱动），Windows 里看不到麦克风 | ❌ | ✅ 摘机/振铃/来电号码检测很在行 | 185–200 元 | 当麦克风 **5%** / 做检测 90% | ⚠️ 一半 |

> 而调研最大的意外是 **R0**：市面上本来就有"**把座机听筒接到电脑当 USB 耳麦用**"的成品适配器（RJ9→USB，Windows 免驱识别为麦克风+扬声器，全双工）。**它绕开了整个电话线的物理难题，95% 成功率、百元价位。**

## 2. 必须知道的五个技术真相（调研后修正）

### 真相 0（最重要）：话机需要"局端供电"，而电脑给不了
RJ11 那一对线**本身不带电、不做信号处理**，它只是两根铜线。
- **要通话**：话机必须拿到局端的**环路馈电**（约 −48V DC，环路电流 20–40mA）。没电流 → 听筒里死一样安静、没有拨号音。
- **要响铃**：需要**铃流 20–25Hz / 60–90V AC**（新式电子铃 16–60Hz 都行，老式机电铃必须接近 20Hz）。
- **摘机检测**：本质就是"线路上有没有环路电流"，通常用光耦做电流检测。

👉 **这条推论决定了整个方案选型：把"整机话机"接到电脑，器件必须自己提供馈电+铃流（这就是 ATA 为什么贵）；而"只取听筒"就完全绕开了这个问题——因为听筒是驻极体麦克风+动圈喇叭，本质就是一个耳麦。**

### 真相 1：录音盒只"偷听"，而且**故意不让你当麦克风用**
- 录音盒是**高阻并联**在电话线上偷听语音的，它**不给话机馈电、不产生振铃**。
- 更关键：这类信创录音盒**采用私有 USB 协议，"摒弃了传统 USB 声卡（UAC）/HID 标准类方案"**，目的是"独占性控制，避免操作系统把设备识别成通用音频设备、防止其他应用抢占通道"，必须装厂商的签名内核驱动。
- **后果：它检测摘机/振铃/来电号码很在行（90%），但 Windows 录音设备里看不到它的麦克风（当麦克风成功率约 5%）。**
- 💡 **下单前必问客服一句话**："这个盒子插上电脑后，Windows 的『录音设备』里能不能直接看到一个麦克风？" 这一句能省掉整条弯路的钱。

### 真相 2：USB 语音猫看着很美，实际是坑
- 协议层面它**确实**支持你要的一切（IS-101/V.253 语音命令集：`+FCLASS=8` 进语音模式、`+VLS` 选模拟源/目标如 n=7 摘机、`+VDR` 振铃报告、`+VTS` 发 DTMF）。
- 但 **① 它不向话机馈电**（话机接上完全静默，必须再串线路模拟器 ¥700+）；**② 它在 Windows 里是 legacy "UniModem Half-Duplex Audio Device"，不是 UAC 麦克风**，现代软件（Teams/Whisper/语音输入）基本看不到它；**③ 半双工 8kHz**、**④ 驱动是 2010 年前后产物**，Win10/11 下签名兼容问题不断。
- 连 IVR 软件厂商 VoiceGuide 官方都写着"**不推荐使用语音猫**"。**成功率 25%，不推荐。**

### 真相 3：微信输入法的语音**没有对外接口，接不进去（放弃）
- 无 API、无命令行、无输入设备重定向，社区无可用方案。唯一灰色路径（虚拟声卡喂声 + 模拟长按按钮）要求窗口焦点、坐标敏感、升级即失效，还要叠它自己服务器往返 2–4 秒。
- **结论：不作为主链路。** 自己做的本地流式 ASR 更快、更稳、完全可控。

### 真相 4：延迟的大头是"端点检测"，不是识别模型
延时 = **①VAD 判定你说完（0.5–1.2s）+ ②ASR 出字（0.1–0.8s）+ ③模型应答（~1s 首字）**。
"流式"的本质是让 ①② 边说你边出字。

### 真相 5（反直觉）：**别把电话音频上采样到 16k**
- 实测：把 8kHz 音频上采样到 16kHz 再喂 ASR，**WER 反而升高约 11%**（重采样伪影破坏频谱特性与能量对齐）。
- 正确做法：**整条链路保持 8kHz**，选原生支持 8k 的模型/接口（Silero VAD 支持 8k；腾讯云/火山/讯飞都接受 8k PCM）；若模型强制 16k，用高质量重采样（soxr HQ / `scipy.signal.resample_poly`）且**在模型侧做**，不要在采集链路提前做。
- ⚠️ **好消息**：走 ★R0 路线（RJ9→USB 适配器）时，听筒话筒是被 USB 声卡直接采样的，**出来的就是宽带音频（16k/48k），根本不存在 8kHz 窄带问题**——这是 R0 相对 ATA/录音盒路线的又一个隐性优势。
- 另注：**Silero VAD 必须用 ≥ v6.2**（官方 issue #606：旧版在 8kHz 窄带下会"安静背景误触发、有噪声又漏人声"，维护者确认 6.2 已修）。

### 3.2 硬件确定后的目标架构（以 ★R0 听筒直连为例）

```
        ┌──────────────────────────┐
        │ 红色座机（底座保留不动）    │
        │  ┌─────────┐             │
        │  │  听筒    │ 4P4C 手柄线  │      叉簧开关（原机铜弹片）
        │  │ 麦克风+喇叭│───┬────────┼──────────┐
        │  └─────────┘   │        │          │
        └────────────────┼────────┘          │
                         │                   │
                  [RJ9→USB 适配器]      [Arduino Pro Micro]
                  (标准 UAC 声卡)       (模拟 USB 键盘按键)
                         │                   │
                         └─────────┬─────────┘
                                   ▼  USB
                    ┌──────────────────────────────────┐
                    │  PC · 电话服务程序 phone_dsh.py    │
                    │  状态机：                          │
                    │   摘机事件 → 播拨号音 → 开麦        │
                    │   音频流 → VAD → 流式ASR → 出字     │
                    │   挂机事件 → 定稿 + 回车发送         │
                    │   TTS → 送听筒声音                 │
                    └──────────┬───────────────────────┘
                               ▼ 模拟按键/粘贴
                     DSH Web 输入框（3080）/ 指定对话窗
```

> ATA 路线（R4）则替换上半部分为：`话机 ── RJ11 ── FXS 网关 ── 网络 ── PC(SIP/pjsua2)`，
> 此时摘机/挂机/振铃全部由网关原生提供，不需要 Arduino 开关。

### 4.1 ★推荐落地组合（调研后定版）

### 方案 A｜最省事（¥100–330，当天能用）→ **我推荐从这个开始**
1. 淘宝搜 `RJ9转USB 耳机适配器`，选带音量/静音按键的（¥100–250）；
2. 把话机**手柄**从底座上拔下来，插进适配器的 RJ9 母口；
3. 插 USB → Windows 直接多出一个标准 USB 麦克风+扬声器，全双工，任何软件都能用。
**得到**：对着电话听筒说话=对着电脑麦克风说话；AI 的声音能**从听筒里念给你听**。这就是"语音输入终端"的核心体验，先拿到手。
**缺**：摘机/挂机检测、真振铃。

### 方案 B｜加"提机即通"的开关（+¥50–150）
- 用话机底座的**叉簧开关（hook switch）** 接一块 **Arduino Leonardo / Pro Micro**（能模拟 USB 键盘）+ 5 行代码；
- 提机 = 自动发一个按键 → 触发"开始录音"；挂机 = 松开 → "停止+上屏"。
- **这是"提机即通、挂机即断"的完整闭环**，成本极低，且完全可逆（不破坏话机）。DFRobot 那个 ESP32 项目用的就是原机铜弹片，思路一样。

### 方案 C｜真响铃（"模拟来电"）（+¥300–700）
- 上游加一台 **Grandstream HT801 / 国威小 PBX**，SIP 一呼 → 话机**机械铃真的响**；
- 或者 **零成本**：电脑扬声器播一段电话铃声（体感差一点，但没风险）。
- ⚠️ 注意：在 R0 路线上，**话机底座不再接电话线，铃是不会响的**（因为没接线路，也就没有铃流）。要真响铃必须上 ATA/PBX ——这也是 R4 的独特价值。

### 组合结论

| R3 语音猫 | 750+ | 理论上全套，实际体验最差 | ❌ 不推荐 |

### 4.2 语音链路定版（调研完成，30+ 次检索）

### 结论速览

| 问题 | 结论 |
|---|---|
| 微信输入法能否当管道 | **不能**（无 API/CLI；结果直接注入焦点窗口，程序拿不到增量文本；实测还有"整段回溯重写"抖动） |
| 最优本地流式 | **FunASR 双通道**：Paraformer 流式（480ms 出临时字）+ SenseVoice-Small 断句后整句重跑修正 |
| 中文精度对比 | FunASR CER **8.17%** vs whisper.cpp large-v3-turbo **23.15%** → **约 2.7 倍差距**（同硬件同测试集） |
| 最省事零代码 | **CapsWriter-Offline**（6.8k★，仅 Windows，支持 SenseVoice/Paraformer/Fun-ASR-Nano/Qwen3-ASR，**按住 CapsLock 说话、松手上屏**） |
| 零成本兜底 | **豆包输入法 Windows 版**（免费、免按模式、首字 ~1s、中英混说 >95%、无时长限制；但同样不可编程） |
| 云端兜底 | 腾讯云实时识别大模型2.0版 **1.0 元/小时**（每月免费 5h）；火山首字 ~480ms 约 4.5 元/小时 |
| 显存 | FunASR 仅 400–900MB；而 Whisper turbo 峰值 4.7GB + 本地 8B LLM 7.8GB 会**在 Windows 上互相抢算力**（无 MPS 支持，只能时间片轮转） |

### 主链路（全本地、可编程）

```
USB声卡(16k 宽带) → Silero VAD ≥v6.2 端点检测
                          ↓
              ┌───────────┴───────────┐
       通道1（低延迟）             通道2（高精度）
       paraformer-zh-streaming     SenseVoice-Small
       chunk_size=[0,8,4]          断句后整句重跑
       480ms 出临时字               CER 7.8%
              └───────────┬───────────┘
                          ↓
              键盘注入（SendInput）→ DSH 输入框
```
**端到端延迟预算**：采集缓冲 20–40ms + VAD <1ms/chunk + 流式 ASR 480ms + 注入 <10ms ≈ **首字 0.5–0.6 秒**。

### ★ 关键发现：零代码路线竟然几乎"插件式"成立
**CapsWriter-Offline 的触发方式是"按住 CapsLock 说话、松开上屏"——这是一个标准键盘长按事件。**
而我们的叉簧开关（提机/挂机）本来就是靠 **Arduino Pro Micro 模拟 USB 键盘按键** 实现的：
**提机 = 按下 CapsLock → 开始录音；挂机 = 松开 CapsLock → 出字上屏。**
👉 **也就是说，方案 B 的开关可以和 CapsWriter 直接对接，P2 阶段存在一条"几乎零代码"的实现路径。** 这大幅降低了整个项目的工程量，进可攻退可守：先用它快速验收体验，不够再自己写双通道流式。

### 键盘注入的三个坑（必踩，提前规避）
1. **权限必须对齐**：要往管理员权限的程序里注入，注入工具本身也必须以管理员运行（CapsWriter 文档明确写了）。
2. **IME 状态**：焦点在英文输入法状态时注入中文会乱码/丢失 → 注入前检测并切换 IME，或用剪贴板粘贴替代逐字注入。
3. **剪贴板污染**：用剪贴板方案要保存/恢复原内容。

### 命令词闭环（必须做，否则"说完不能发"）
语音里说"**发送**"→ 回车；"**换行**"→ Enter；"**清空**"→ 全选删除。自己做命令词映射（只有 Win+H 原生支持说"换行"）。

### 一个必须说清的现状

查客户端源码 `core/client/output/result_processor.py` 第 201 行：

```python
if not message.is_final:
    return          # 非最终结果直接丢弃
```

👉 **CapsWriter 只在"松开按键"时才把文字上屏**，中间结果只用于控制台显示。
所以它满足"低延迟"（0.2–0.5s），但**不满足"边说边看字"**。

**✅ 已决定（2026-09-04 用户拍板）：不做"边说边看字"。**
理由：用座机时"左手握着听筒"本身就是物理提示——用户清楚自己正在录音，不需要屏幕上的实时文字反馈。
→ 因此 **P2 不写自研双通道**，省下 1–2 天工作量，继续用 CapsWriter。

**场景**：握着听筒说话时手可能松开鼠标、焦点被切走，Ctrl+V 粘不到目标输入框。

**改动**（本项目对 CapsWriter 的唯一代码级改动）：
